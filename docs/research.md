# Filter by folder before the model reads

The best fully local stack for Sentinel's successor in November 2026 copies the pattern large companies use. **Permissions are resolved by a dedicated authorization service at query time and pushed down as a pre-filter into the vector search. The final hits are re-checked before any chunk, citation or cache entry is created, and the LLM never decides who sees what.** Concretely: **OpenFGA v1.22** holds users, groups, folders and per-user grants. **Qdrant 1.20** stores chunks with a `folder_id` payload index and runs filtered dense plus BM25 hybrid search. **PostgreSQL** is the system of record (documents, manifest, sessions, audit, job queue via Procrastinate). **Docling 2.147** parses files, and **Qwen3-Embedding-0.6B** and **Qwen3-Reranker-0.6B** handle embedding and reranking on both machines. The answer model runs on **Ollama 0.40.x**: **Qwen3.5-4B** on the CPU-only laptop and **Qwen3.5-9B** or **gpt-oss-20b** on the RX 9070 XT desktop, with JSON-schema output that cites chunk IDs. **FastAPI 0.162** fronts it as a backend-for-frontend with HttpOnly session cookies, and a React/TanStack SPA streams answers over SSE. Laya stays in front as the prompt gate. This matters because the most common real-world leaks are not exotic. They come from post-filtering that hands unauthorized text to the app layer, from stale ACL copies after revocation, and from misconfigured approximate indexes that silently drop or mix results. Each choice below targets one of those failure modes, and the test plan at the end treats "zero canary leaks" as a hard release gate rather than an LLM-judged score. One identical Docker Compose definition covers both machines; only a hardware profile and the model tags change.

## Production RAG enforces permissions in three places, never in the prompt

Enterprise systems converge on one shape. Microsoft's ISE team, indexing SharePoint into Azure AI Search, stores `allowedUsers`/`allowedGroups` per document, normalizes them to stable directory IDs, and filters at query time so that **"Authorization runs before documents are returned to the caller"**. The same write-up names the failure modes to design against: post-retrieval filtering means data has already reached the app layer, unexpanded groups cause "silent overexposure", and revocations that aren't pushed leave a revoked user seeing content until the next ingestion run ([Microsoft ISE](https://devblogs.microsoft.com/ise/sharepoint-doc-level-access/)). Auth0's reference RAG integration takes the opposite approach. Its `FGARetriever` retrieves candidates (25 in the Vercel variant) and then batch-checks each against OpenFGA ([Auth0 AI](https://auth0.com/ai/docs/get-started/authorization-for-rag)). That is simple, but it suffers top-k starvation when most candidates are filtered out, and it lets restricted text into application memory. OWASP's LLM08:2025 explicitly calls for **"permission-aware vector and embedding stores"**, dataset partitioning and **"detailed immutable logs of retrieval activities"** ([OWASP LLM08](https://genai.owasp.org/llmrisk/llm082025-vector-and-embedding-weaknesses/)). LLM01 adds that RAG does not prevent indirect prompt injection, so sensitive functions belong in code, not in the model ([OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)).

The design that combines these lessons has three enforcement points. First, at query time the API asks the authorization engine for the set of folders the user can view, using a fresh-consistency read. Second, that set becomes a server-built `folder_id IN (...)` filter applied to *both* the dense and the lexical legs of the hybrid search, so unauthorized chunks are never scored or returned. Third, after reranking, the surviving document IDs are batch-checked again, and their Postgres rows are confirmed live and not deleted, before anything reaches the LLM, the citation stream or a cache. The model is told to cite only provided chunk IDs, and the server discards any citation outside the retrieved-and-authorized set, rendering titles and links from its own metadata. Laya keeps its Sentinel role as a pre-retrieval gate that can block or downgrade a prompt. It is an additional control, not the ACL mechanism. ACLs stay deterministic.

Filtering by **folder** rather than by user or document is the key simplification. Chunks carry only `folder_id` (plus `doc_id`), which changes only when a file moves, while the user→group→folder mapping lives in the authorization store and is resolved per request. Granting or revoking access therefore takes effect on the next query with no re-indexing, which removes the revocation window the ISE team documents. The authorized set is tens of folders, so the filter list stays small.

## OpenFGA models groups, grants and folder inheritance; resolve it fresh on every query

OpenFGA and SpiceDB are the two mature, self-hostable Zanzibar-style engines. OpenFGA is at **v1.22.0 (Oct 6, 2026)** ([OpenFGA releases](https://github.com/OpenFGA/OpenFGA/releases)). SpiceDB is at **v1.56.2**, with authzed-py 1.25.0 ([AuthZed changelog](https://authzed.com/changelog)). OpenFGA is the better fit here. Its ListObjects "returns all objects of a given type that a user has a relationship with", and StreamedListObjects is available in the Python SDK ([OpenFGA docs](https://openfga.dev/docs/getting-started/perform-list-objects)). Auth0's RAG tooling is built on it, it can use the same Postgres you already run, and SpiceDB's accelerated listing feature (Materialize) is available only on the managed Dedicated product ([AuthZed changelog](https://authzed.com/changelog)). Cerbos is a credible stateless alternative. Its PlanResources compiles policy into a filter, but it ships adapters only for SQLAlchemy, Prisma and LangChain/ChromaDB, not Qdrant or pgvector ([Cerbos](https://docs.cerbos.dev/cerbos/latest/recipes/query-plan-adapters/)), so you would write that adapter yourself. Oso's documented list filtering runs on Oso Cloud, which conflicts with the fully-local requirement ([Oso](https://www.osohq.com/docs/develop/enforce/list-filtering)).

The model is small. `group#member` can contain users or nested groups. `folder` has `parent`, `owner`, `editor` and `viewer` relations (each assignable to a user or to `group#member`), with `viewer` also inherited from the parent folder. `document` inherits `can_view` from its folder. A `system#admin` relation governs who may write grants. Deny-by-default is inherent, because no tuple means no access. Use explicit "but not" blocks sparingly: OpenFGA documents that **exclusion and intersection relations are more expensive to evaluate than unions** ([OpenFGA docs](https://openfga.dev/docs/getting-started/perform-list-objects)). Separate "can manage grants" from "can read content" so an admin account does not silently read HR files. Every admin action writes and deletes tuples through the API, never directly, and appends a row to an immutable `audit_events` table.

Two OpenFGA release notes explain why the defense-in-depth re-check exists. v1.19.0 fixed **GHSA-5278-rrxc-mgf7, where StreamedListObjects could return an object that should have been excluded during an error**. v1.17.1 fixed a cache race that could return stale tuples. v1.22's read replicas route everything except `HIGHER_CONSISTENCY` reads to a possibly lagging replica ([OpenFGA releases](https://github.com/OpenFGA/OpenFGA/releases)). So pin at least 1.22 and request higher consistency for the ListObjects call that builds the retrieval filter. Treat the final batch check as cheap insurance against a future engine bug.

Identity follows **RFC 10017 (BCP 212, Aug 2026)**. It ranks a Backend-for-Frontend as the most secure browser pattern, strongly recommends it for business apps, and states "The BFF MUST enable the HttpOnly flag for its cookies" ([RFC 10017](https://datatracker.ietf.org/doc/rfc10017/)). FastAPI is the BFF. It keeps opaque server-side sessions in Postgres, never puts JWTs or permission claims in the browser, and hashes passwords with **Argon2id at OWASP's minimum m=19 MiB, t=2, p=1** ([OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)). Add CSRF tokens on state-changing requests and a CLI `create-admin` bootstrap. A self-hosted OIDC provider (Pocket ID, Authentik) is an optional later add-on that creates the same local session. Map its groups to OpenFGA groups only through an explicit admin sync, never by trusting live claims.

## Qdrant 1.20 beats pgvector on the one property that matters: filtered search that still returns k results

The vector store must return k results for a user who can see only one department, without leaking across departments. Here the candidates differ sharply. pgvector (README at v0.8.7) applies filters *after* the approximate index scan: **with the default `ef_search` of 40 and a filter matching 10% of rows, only about 4 rows survive on average**. Iterative scans fix this only when enabled, and they stop at `hnsw.max_scan_tuples` (20,000 by default) ([pgvector](https://github.com/pgvector/pgvector)). ClickHouse's October 2026 guide shows the trap: if the index returns 10 rows and the WHERE clause rejects 9, "the query silently returns one result" ([ClickHouse](https://clickhouse.com/resources/engineering/scale-vector-search-postgres)). A user who sees one of ten departments is exactly that documented failure case. Postgres row-level security does not escape it, because RLS predicates are just more filters on the same post-filtered scan.

Qdrant filters *during* graph traversal. A cardinality-aware planner scores small matching sets exactly, and otherwise walks a filterable HNSW graph that has extra edges between points sharing an indexed payload value. Those edges exist **only if the payload index is created before HNSW is built** ([Qdrant filtering](https://qdrant.tech/articles/vector-search-filtering/)), so the collection bootstrap must create the `folder_id` keyword index first. Qdrant 1.20 (Oct 22, 2026) added **native BM25 scoring on full-text payload indexes**, which can be fused with dense search or used for rescoring, so hybrid search needs no separate sparse model ([Qdrant 1.20](https://qdrant.tech/blog/qdrant-1.20.x/)). Version 1.19's per-query `idf` parameter can scope BM25 statistics to a corpus filter, keeping term rarity in HR from shaping engineering scores ([Qdrant multitenancy](https://qdrant.tech/documentation/guides/multiple-partitions/)). Recent releases also added audit logging (1.17), strict-mode memory guardrails and per-component memory monitoring (1.18), and internal auth by default when an API key is set (1.20) ([Qdrant 1.18](https://qdrant.tech/blog/qdrant-1.18.x/); [Qdrant 1.20](https://qdrant.tech/blog/qdrant-1.20.x/)). Leave ACORN off. Qdrant recommends it for multiple strict filters, not for a single indexed field ([Qdrant filtering](https://qdrant.tech/articles/vector-search-filtering/)).

| Option | Filtered recall behaviour | Hybrid | Fit |
|---|---|---|---|
| **Qdrant 1.20 + Postgres** | In-graph filtering; k results whenever k matches exist | Native BM25 + dense fusion | **Recommended** |
| Postgres + pgvector 0.8.7 | Post-filter; needs iterative scan or per-department partitions | Native FTS or ParadeDB (AGPL) | Simplest ops, strongest transactions; viable "lean mode" |
| Weaviate 1.40 | Allow-list pre-filter, ACORN default | Built-in | Supports only the latest 3 minors, roughly 2-month cadence ([Weaviate](https://docs.weaviate.io/weaviate/release-notes)) |
| LanceDB (embedded) | Prefilter default; filter applies to both FTS and vector legs ([LanceDB](https://docs.lancedb.com/search/filtering)) | Yes | Lightest, but multi-process writes and auth are your problem |
| Milvus 3.0 / Lite | Pre-filter; partition-key isolation "relatively weak"; Lite has no auth or RBAC ([Milvus](https://milvus.io/docs/multi_tenancy.md); [Milvus Lite](https://milvus.io/docs/milvus_lite.md)) | Sparse + dense | Heavier than needed |

The steelman for pgvector is real. One transactional store means a file move or delete and its chunk update can never disagree. The split design covers that gap differently: Postgres stays authoritative, and the post-rerank re-check confirms every hit's document row before use, a pattern the ClickHouse guide also recommends when adding a dedicated vector store ([ClickHouse](https://clickhouse.com/resources/engineering/scale-vector-search-postgres)). Do not use Qdrant's `is_tenant` sharding or one collection per department. With a handful of departments, a single collection with a `folder_id` index is the documented pattern ([Qdrant multitenancy](https://qdrant.tech/documentation/guides/multiple-partitions/)). No neutral 2026 benchmark compares filtered recall across these engines, so run your own recall@k test per persona against brute-force ground truth.

## Two machines, one model family: Qwen3.5 on Ollama, with ROCm on Linux for the 9070 XT

Pin the embedding model, not the chat model, across machines. The index is only portable if both machines embed with the same model and dimensions. **Qwen3-Embedding-0.6B** (Apache 2.0, 1024 dimensions with Matryoshka truncation, 32K context, MTEB English v2 70.70) is the right shared choice. It runs on the laptop CPU and leaves VRAM headroom on the desktop ([HF Qwen3-Embedding](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)). Record `embed_model` and dimensions in the collection metadata. **Qwen3-Reranker-0.6B** scores 65.80 on MTEB-R against 57.03 for bge-reranker-v2-m3 in vendor tests ([HF Qwen3-Reranker](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)). Rerank about 30 candidates on the laptop and 50–100 on the desktop. Decoder-based rerankers are slower per pair on CPU, so bge-reranker-v2-m3 is the laptop fallback if latency hurts. The reranker can differ per machine without touching the index.

For answers, **Qwen3.5** (March 2026, Apache 2.0, 262K context) leads its size classes. The **9B scores 32 and the 4B 27** on the Artificial Analysis index, at roughly 6 GB and 3 GB in 4-bit. Both also hallucinate around 80% of the time when answering from memory alone ([Artificial Analysis](https://artificialanalysis.ai/articles/qwen3-5-small-models)), which is why the cite-or-refuse contract below is mandatory, not optional. The laptop has only about 5 GB free in normal use, so **Qwen3.5-4B Q4** is the ceiling there (Granite 4.0 H-Micro is the 3B fallback, with IBM claiming over 70% lower RAM on long inputs ([IBM](https://www.ibm.com/new/announcements/ibm-granite-4-0-hyper-efficient-high-performance-hybrid-models))). On the desktop's 16 GB, **Qwen3.5-9B at Q6/Q8** fits with room for long context plus the embedder and reranker. **gpt-oss-20b** (21B total, 3.6B active, MXFP4 within 16 GB) is the stronger-reasoning alternative, though it requires the harmony response format ([HF gpt-oss-20b](https://huggingface.co/openai/gpt-oss-20b)). Community measurements on the 9070 XT with ROCm 7.x report **gpt-oss:20b at 91.9 tok/s and Qwen3 14B Q4 at 52.2 tok/s, while a 27B-A3B MoE that spills past VRAM collapses to 6.3 tok/s** (dev.to ROCm 7.2 guide, cited in the hardware notes without a full URL). So stay under 16 GB, and use non-thinking mode or low reasoning effort for RAG latency.

The runtime is **Ollama**, now at **v0.40.15 (Nov 3, 2026)** with a ROCm build ([Ollama releases](https://github.com/ollama/ollama/releases)). The user's installed 0.12.10 predates Vulkan acceleration, which shipped in 0.12.11 ([Phoronix](https://www.phoronix.com/news/ollama-0.12.11-Vulkan)), so upgrade. The desktop should run **Linux**. Ollama's Linux build supports the 9070 XT with the ROCm v7 driver, but its Windows support table stops at RDNA3 ([localaimaster](https://localaimaster.com/blog/rx-9070-xt-local-ai)), and ROCm 7.2 made RDNA4 official on Linux ([runaihome](https://runaihome.com/blog/rdna4-vulkan-vs-rocm-local-llm-benchmark-2026/)). The Docker image is `ollama/ollama:rocm` with `/dev/kfd` and `/dev/dri` passed through ([Ollama Docker](https://docs.ollama.com/docker)). Prefer ROCm over Vulkan here. Vulkan wins decode speed for small and MoE models, but ROCm wins prompt processing by about 40–45% and has lower time-to-first-token, and RAG is prefill-heavy ([runaihome](https://runaihome.com/blog/rdna4-vulkan-vs-rocm-local-llm-benchmark-2026/)). Skip vLLM on this card for now. On gfx1201 it trailed llama.cpp (48 vs 62 tok/s on Qwen3.5-9B) ([ivangotoy benchmark](https://github.com/ivangotoy/llama-server-rdna4-vulkan)), and AMD's own validation targets Instinct GPUs ([AMD ROCm blog](https://rocm.blogs.amd.com/software-tools-optimization/vllm-omni/README.html)). Laya runs on the same GPU via PyTorch ROCm 7.14 wheels with a gfx1201 device package (`LAYA_DEVICE=rocm`) and on CPU on the laptop. Because every runtime speaks an OpenAI-compatible API, the app only switches base URL and model tag.

Grounding uses Microsoft's spotlighting result. **Datamarking cut document-Q&A injection success to 8.0% on GPT-3.5 and 1.0% on GPT-4 without hurting task scores, while plain delimiters are bypassable and base64 encoding degrades weaker models** ([Spotlighting](https://arxiv.org/html/2403.14720v1)). Each chunk is wrapped as `<doc id="S3">` with datamarked body text. Decoding is constrained to a JSON schema (`answer`, `citations[]`, or `insufficient_evidence`), and server code validates every cited ID. Nobody has measured spotlighting on 2026 open models, so it lowers injection risk without bounding it. That is one more reason the model never gets a tool that can change grants or query outside the user's filter.

## Ingestion with Docling, a Postgres manifest and metadata-only folder moves

**Docling v2.147.0 (Nov 4, 2026)**, MIT-licensed, parses PDF (including scanned, via RapidOCR or Tesseract), DOCX, PPTX, XLSX, HTML, Markdown and CSV ([Docling releases](https://github.com/docling-project/docling/releases)). It sends nothing remote unless `enable_remote_services=True`, models are pre-downloaded with `docling-tools models download`, and it has built-in caps on file size, page count, decompressed bytes and image pixels ([Docling options](https://docling-project.github.io/docling/usage/advanced_options/)). Avoid PyMuPDF/pymupdf4llm (AGPL) ([PyMuPDF](https://pymupdf.readthedocs.io/en/latest/about.html)). Treat marker's weights (Open RAIL-M with a $5M revenue cap) ([marker](https://github.com/datalab-to/marker)) and MinerU's custom terms ([MinerU license](https://raw.githubusercontent.com/opendatalab/MinerU/master/LICENSE.md)) as exceptions needing sign-off. Note that Docling's benchmark position is contested. Datalab's self-reported olmocr-bench puts Docling at 50.3 versus Marker's 76.0 ([marker](https://github.com/datalab-to/marker)), so test it on your scanned financials before trusting it. Docling's **HybridChunker** splits by document structure using the embedding model's own tokenizer, merges small peer sections and repeats table headers across splits ([Docling chunking](https://docling-project.github.io/docling/concepts/chunking/)). Prepend a deterministic breadcrumb (folder / title / section / page) to each chunk before embedding and BM25 indexing. Anthropic's contextual retrieval cut top-20 retrieval failures **by 49% with contextual embeddings plus contextual BM25, and by 67% when reranking was added** ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)). A local LLM can generate richer context on the desktop.

Indexing is a Postgres manifest (stable `doc_id` UUID, path, `folder_id`, size, mtime, SHA-256, parser/chunker/embedder versions, status) driven by **Procrastinate**, an MIT-licensed Postgres-backed queue with queueing locks, retries and cron tasks, so no Redis is needed ([Procrastinate](https://procrastinate.readthedocs.io/en/stable/)). A file watcher (watchfiles) only triggers jobs. A periodic reconcile scan is the source of truth, because bind mounts often drop inotify events. Write each new chunk version under a new `doc_version` and flip the active version in one transaction. A move from `hr/` to `management/` shows up as the same hash at a new path and becomes a metadata-only `set_payload` on the document's chunks, with no re-embedding. Because the filter is applied live, a chunk is never briefly visible to the wrong department. Uploads follow the OWASP File Upload Cheat Sheet: extension allowlist plus magic-byte check, UUID filenames, decompressed-size limits (DOCX and XLSX are ZIP containers), and storage outside the webroot ([OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)). The parser worker runs with `--network none`, a read-only root and memory/CPU/time limits. Injection-looking text (hidden text, zero-width characters, instruction phrases) is flagged on the chunk for admin review, not silently dropped. On the 15 GB laptop, OCR-heavy ingestion competes with the LLM for RAM, so run bulk indexing on the desktop and limit the laptop to incremental jobs.

## App stack and deployment: FastAPI BFF, React SPA, one Compose file with hardware profiles

The backend is **FastAPI 0.162.x**. Pin the minor version, because 0.160.0 and 0.162.0 both shipped breaking parameter changes ([FastAPI releases](https://github.com/fastapi/fastapi/releases)). It uses async **SQLAlchemy 2.0.57**, the 2.0 maintenance line, and moves to 2.1.8 only after testing, as the project itself advises ([SQLAlchemy](https://www.sqlalchemy.org/blog/2026/09/08/sqlalchemy-2.1.0rc2-released/)). Migrations use Alembic, organized as a **uv workspace** (`apps/api`, `apps/worker`, `packages/core`) with one lockfile and PEP 735 dependency groups ([uv workspaces](https://docs.astral.sh/uv/concepts/projects/workspaces/); [uv dependencies](https://docs.astral.sh/uv/concepts/projects/dependencies/)). Answers stream over SSE using the **AI SDK UI message stream protocol** (`x-vercel-ai-ui-message-stream: v1`, `text-delta`, `source-document` and custom `data-*` parts), which `useChat` consumes directly from a Python backend ([AI SDK](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol)). Emit `source-document` parts only for chunks that passed the final check. The frontend is a React 19 + Vite + TanStack Router/Query/Table/Form SPA with Tailwind v4 and shadcn/ui, served from the same origin as `/api` so cookies stay first-party. TanStack Start's SSR adds a Node BFF that FastAPI already provides, and its 1.0 GA date conflicts between sources ([TanStack](https://tanstack.com/blog/announcing-tanstack-start-v1); [Appwrite](https://appwrite.io/blog/post/tanstack-start-stable-appwrite-sites)).

Compose runs `postgres`, `openfga` (Postgres datastore), `qdrant`, `ollama` (profiles `cpu` and `rocm`), one-shot `migrate` and `model-pull` services, `api`, `worker`, `laya`, and `caddy` (static SPA plus `/api` reverse proxy with SSE buffering off). Everything is bound to 127.0.0.1, uses healthcheck-gated `depends_on`, and keeps secrets in `.env`. On the laptop, running Ollama natively instead of in Docker saves some memory. Observability uses OpenTelemetry with manual `retrieve`/`rerank`/`generate` spans exported to **Phoenix** behind an optional profile. Langfuse v4 self-hosting asks for **at least 4 cores and 16 GiB** plus ClickHouse and MinIO, which exceeds the laptop ([Langfuse](https://langfuse.com/self-hosting/deployment/docker-compose)). Keep prompt and completion capture off by default. Note that the GenAI semantic conventions have moved to a separate repository with no releases yet ([OTel GenAI](https://opentelemetry.io/docs/specs/semconv/gen-ai/)). The audit trail is the Postgres table, never sampled traces. It records which chunk IDs each query returned to whom.

## Prove non-leakage deterministically, then red-team the chat

LLM-judged evaluation cannot guarantee permissions. Deterministic retrieval-layer tests can. Five layers, in order of authority:

1. **Resolver tests.** Hypothesis property tests generate random group and folder trees with nested groups, inheritance and blocks, then assert that the folder set from OpenFGA equals a brute-force oracle.
2. **Canary tests.** Integration tests on real Postgres, OpenFGA and Qdrant (Testcontainers) seed unique canary tokens in every restricted folder. For every persona, they assert that no canary appears in retrieved chunks, `source-document` parts, citations, answers, search or autocomplete endpoints, or result counts.
3. **Revocation and move scenarios.** Revoke a grant or remove a group member and query immediately. Move a file and query. Delete a file and query. Repeat each with warm caches (semantic, reranker or answer caches must be keyed per user and permission version).
4. **Recall tests.** A recall@k test per persona against brute-force ground truth catches the misconfigured-index failure, for example a `folder_id` index created after HNSW was built.
5. **Endpoint and red-team tests.** BOLA/BFLA tests cover admin and document-download endpoints. A **promptfoo** red-team run as a low-privilege user uses the `rbac` plugin and its relatives (RAG document exfiltration, cross-session leak) ([promptfoo](https://www.promptfoo.dev/docs/red-team/plugins/rbac/)), with a custom assertion that fails on any canary string.

**DeepEval 4.2.0**, which propagates pytest exit codes to CI ([DeepEval](https://deepeval.com/changelog/changelog-2026)), scores faithfulness and context precision per persona with a local judge. Its scores are advisory, while the canary suite is the merge gate.

## Conclusion

The central change from Sentinel is moving the source of truth about access out of the retrieval index and into a live authorization graph. Chunks know only their folder. Who may see that folder is asked fresh on every query, and the answer is checked twice. That one move makes revocation instant, makes folder moves cheap, and reduces "never leaks" to two testable properties: the filter set is correct, and the index honors the filter. Both can be proven with canaries and brute-force oracles instead of hoped for with prompts. It also explains why the vector database decision hinges on filtered-recall semantics rather than raw speed, and why pgvector, despite its transactional appeal, is the riskier default for department-scoped users.

The hardware split argues for one architecture with two model tiers, not two apps. The laptop is a functional but RAM-starved replica, best used for development and incremental indexing. The desktop's 16 GB card comfortably serves a 9B to 20B answer model plus the embedder, reranker and Laya, provided it runs Linux with ROCm. The open risks are empirical rather than architectural: Docling's quality on your scanned financial PDFs, the citation faithfulness of 4–9B models on your own documents, and spotlighting's effectiveness on 2026 open models. None of these has a trustworthy public benchmark, so the per-persona evaluation set is the first thing to build, before the UI.
